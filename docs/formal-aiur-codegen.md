# Compiled Aiur programs: codegen and caching

Status: implemented. Baseline: `formal-aiur-perf-ffi`, which persists compiled
programs as `AIURIMG` version 1 files (`crates/aiur/src/artifact.rs`) and
feeds the `kernel!` procedural macro from those files. This design
separates code generation from storage. It revises the artifact-fed macro
assumption in [formal-aiur-direct-ffi.md](formal-aiur-direct-ffi.md); that
document's live, in-memory handoff is unchanged.

## Decision

Code generators consume a checked program, not a storage format:

```text
checked bytecode ──────→ native generator ─→ Rust source ─→ build
checked trace plans ───→ CUDA generator ───→ CUDA source ─→ build
        │
        └─────────────→ compiled-program cache
```

- **Native codegen** emits Rust executors from checked bytecode and its
  normalized execution plan only.
- **CUDA codegen** emits trace writers from population plans and placement
  only.
- **The compiled-program cache** stores the certified compiler's output so
  commands avoid recompiling. Neither generator reads it.
- **Store addresses, manifests and bundles** are not part of code
  generation.

## How legacy Aiur handled this

Legacy Aiur kept no compiled-program artifact and no cache.

- **Compiled on every run.** Each command compiled the Lean-authored
  programs in process (`Aggr.compileBackend` →
  `Source.Toplevel.compileWithGroups`).
- **Direct handoff.** The resulting `Bytecode.Toplevel` went to Rust as a
  borrowed Lean object (`AiurSystem.build : @& Bytecode.Toplevel → … →
  AiurSystem`). Rust decoded it (`crates/ffi/src/aiur/toplevel.rs`) and
  returned an opaque system handle. Only verifying keys became bytes.
- **Committed generated code.** Native and CUDA code was generated from the
  Lean programs as source and committed (`crates/aiur/src/trace_codegen/
  programs/*.rs`, `crates/aiur/cuda/generated/**`, about 5 MB in total). It
  was regenerated by hand when a program changed.
- **Ix store for outputs only.** Claims, proofs and compressed proofs were
  Ixon objects in `~/.ix/store`.

The legacy compiler ran in seconds. The certified compiler takes minutes
(IxVM about 7, aggregation about 2, recursion about 1.5), so formal Aiur
needs a cache. Legacy's separation between "compile in process, hand over
directly" and "generate source for the build" is the model this design
keeps.

## Code generation

Code generation runs inside `lake build ix`, before Cargo, and writes into
the build directory, never the source tree. Nothing generated is committed.

```text
lake build ix
  ix_rs                Rust archive without generated code
  formal-codegen       Lean executable: the certified compiler, linking ix_rs
  formal_generated     formal-codegen .lake/build/formal-generated [--cuda]
    1. each program from the shared cache; misses compile concurrently
    2. native/{ixvm,verifier,aggregation}.rs        (aiur-codegen)
    3. CUDA builds only: cuda/{ixvm,verifier,aggregation}/  (aiur-tracegen)
  ix_rs_net            Cargo compiles the generated files into ix
```

### Native executors

The Rust emitter that used to live in the `kernel!` procedural macro is the
ordinary library `aiur-codegen`; the macro is gone. Its input is a checked
program (bytecode and the native execution plan), and its output is Rust
source text. `crates/formal-generated` compiles the generated files with
plain `include!`, so Cargo tracks them as ordinary sources. Cargo never
invokes Lake and never reads a compiled-program artifact.

The emitter's own test (`crates/aiur-codegen-tests`) generates the executor
of a fixture program from its build script and checks it against the
interpreter.

### CUDA trace writers

`aiur-tracegen` is a library over population plans and placement. In a
CUDA build it emits one unit per supported circuit and a Rust binding
(`bundle.rs`) per program; per-circuit units let nvcc compile and cache
them in parallel.

CUDA output is gated by the same selection that enables the `cuda` Cargo
feature (`cudaEnabled` in `lakefile.lean`: `IX_CUDA`, or
`IX_CUDA_TRACE_CODEGEN` or `IX_FORMAL_COMPILED_TRACE=1`, which imply it).

- A CPU build runs only the native emitter: no tracegen work, and any CUDA
  output from an earlier CUDA build is removed.
- The selection is part of the generation step's trace, so switching CUDA
  on regenerates with the CUDA sources, and the build never compiles stale
  CUDA output.
- The writers are compiled and linked with `IX_FORMAL_COMPILED_TRACE=1`
  and selected at run time with `AIUR_GPU_TRACE=compiled`; only IxVM's
  bundle is registered. In a CPU build the GPU population path reports that
  it is unavailable, as before.

### When generation runs

`formal_generated` reruns only when `formal-codegen` itself (the compiler,
the emitters or their Lean callers), a program's source bundle, or the CUDA
selection changed. It rewrites only files whose contents changed, so Cargo
recompiles only executors that actually changed. A native executor's file
records only its fingerprint, so a change that leaves the bytecode and the
execution plan alone, such as regrouping circuits, leaves it
byte-identical. The CUDA files depend on the grouping and also record the
source digest.

The first build on a machine, and the first after a source revision or a
compiler change, pays the certified compile: about 7 minutes for the three
programs, compiled concurrently (IxVM dominates). Every later build, in
any checkout with the same compiler and sources, loads them from the cache
in about 2 seconds.

`ix codegen --out DIR [--cuda]` writes the same sources to a chosen
directory for inspection.

### Fingerprints

Each generated unit carries the fingerprint of exactly what it depends on:

| Generated code | Fingerprint inputs |
|---|---|
| Native executor | bytecode and the native execution plan (the existing `native_fingerprint`, scheme 2) |
| CUDA trace writer | population plans and placement (the existing population description fingerprint, scheme 2) |

At runtime `ix` recomputes these from the loaded program and compares. A
mismatch falls back to the interpreter, or is rejected under
`IX_FORMAL_NATIVE=1`, exactly as now. Since every build generates the
executors for the current programs, a mismatch means `ix` is older than
the programs it runs, for example after an explicit `--aiur-artifact`, and
the message says to rebuild with `lake build ix`.

- A grouping-only change leaves CPU executors valid.
- Changing how the cache stores a program invalidates nothing.
- The fingerprint definitions and schemes are unchanged.

### Semantic encoding stays in `aiur`

The canonical encodings the fingerprints hash (`artifact::program_bytes`,
the description `Writer`) stay in the generic `aiur` crate. They define
program content, not storage. Storage adapters call them; they do not own
them.

## Compiled-program cache

- **Format.** One immutable file per compiled program, using the
  `AIURIMG` codec in `aiur` (version 2: shared table rows and polynomial
  nodes, zstd-compressed; see
  [formal-aiur-direct-ffi.md](formal-aiur-direct-ffi.md#persistent-artifacts)). There are no per-section blobs, no manifest and
  no bundle.
- **Location.** A shared, configurable directory instead of each checkout's
  `.lake/aiur/`: `IX_AIUR_CACHE`, defaulting to `~/.ix/cache/aiur/`. This
  uses the store's caller-named `cacheDir`, not the content-addressed
  store. Files are named by the cache key: the artifact format version,
  the linked compiler's identity, the target and the source digest. Every checkout on a machine
  with matching compiler and sources reuses the same file; differing
  checkouts never collide.
- **Writing and loading.** Writes are atomic: temporary file, then rename.
  On load, the file's digest is checked and the program is checked before a
  handle exists.
- **Failure.** A corrupt or unreadable cache file is a hard error that names
  the file and says to delete it. It is never a silent recompile.
- **Trust.** As before:
  - a locally compiled program is trusted because this `ix` produced it;
  - an explicitly selected file (`--aiur-artifact` and related flags) is
    trusted because the user selected it.

  Proof inputs never select a program.
- **No automatic pruning.** Cache files can be selected explicitly, pinned
  by builds, or kept to verify historical proofs, so whether one is in use
  cannot be decided from the cache directory. Any cleanup command lists
  candidates and deletes only what the user names.

### Optional Ixon storage

If storing compiled programs in Ixon is wanted later, add it behind a
storage adapter: one Ixon blob per compiled program (the same bytes),
selected by configuration. Codegen and fingerprints are unaffected.

## On-demand compilation

There is no setup command.

- **Build.** `lake build ix` warms the cache for the checkout's programs,
  as part of generating their executors.
- **First use.** Any command that needs a compiled program and finds a
  cache miss, for example after the cache was cleared or under another
  `IX_AIUR_CACHE`, compiles it in process with a progress message and
  persists it. Later commands load from the cache.
- **Concurrency.** A command that needs more than one program compiles them
  concurrently: the frontend is imported once and each program compiles on
  its own thread. Generation needs all three; `ix prove --ixe --ixes` and
  the aggregation commands need IxVM and aggregation.
- **Executor check.** Once programs are selected, a linked native executor
  generated from a different program is reported, with the advice to
  rebuild with `lake build ix`; the program runs on the interpreter. Under
  `IX_FORMAL_NATIVE=1` that is an error.

## Packaging

- **The `formal-native` build option and `native-kernels.env` are gone.**
  Lake's dependency tracking replaces them: `ix` always links native
  executors generated for the current programs.
- **Nix.** The Crane-built archives have no generated code; the flake sets
  `nativeExecutors` to false, so the packaged `ix` runs every job on the
  interpreter, with identical results.
- **Rust-only builds.** `cargo build` of the workspace builds
  `formal-generated` empty; only `lake build ix` enables its `executors`
  feature, which needs the generated directory.

## Verify path

The changes go through the verify-path review:
- the cache location and its corruption error;
- the concurrent compile and the executor check;
- the trusted-artifact flags;
- removal of the artifact-fed macro.

Acceptance logic does not change.

## Acceptance checks

- Native and CUDA source generated for IxVM, recursion and aggregation is
  identical to what the artifact-fed macro and tracegen produced, apart
  from the headers and the macro's artifact-tracking constant. The
  resulting proofs on the existing fixtures are byte-identical.
- A grouping-only change leaves the native fingerprints, and the generated
  `.rs` files, unchanged.
- Two checkouts with identical sources share one cache file; a source
  change produces a new file.
- A corrupt cache file fails with the specified error.
- Measure a fresh-clone `lake build ix` with an empty cache, and a rebuild
  with a warm cache, against the sequential 11:12 compile.
- Full Init, Mathlib and GPU runs need separate authorization.
