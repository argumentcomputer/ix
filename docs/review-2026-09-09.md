# Code, documentation, and plan review — 2026-09-09

> **Historical record.** The compiler code, fixtures, runners and documents
> it describes left main on 2026-09-29 when the compiler was rebuilt; links
> to them point to branch `jcb/ixby-archive`.

The implemented boundaries are substantially supported by their proofs,
fixtures, and integration gates. Two reproducible implementation issues need
attention: IxIR₀ rejects identical erased blocks, and the indexed HPT cache
can exceed its selected-read budget after a file replacement. The main
planning gap is the absence of a concrete source-coverage successor to C2.

This is a dated review, not another authoritative plan. The
[roadmap](roadmap.md) continues to own priorities and delivery state.

## Scope and method

Reviewed the working tree based on commit
`5cdf52b96801c224db00cf1a7804f55f17285b82`, including its uncommitted R6, C2,
N2, B1, and B2 work, with Lean `v4.33.0` on x86_64 Linux. The review covered
the documentation and planning structure, public compiler/proof interfaces,
high-risk ingress and identity paths, recent ownership/runtime extensions,
artifact checkers, trust inventory, and build/CI configuration.

This is a boundary and integration review with targeted code inspection,
not an independent proof of every implementation line. Existing theorem
premises were checked against the advertised scope. Compiled regression gates
were rerun, and separate temporary compiled probes reproduced both code
findings. The probes used the existing implementation; no compiler changes
were made. A file-digest comparison confirmed the reviewed input files stayed
unchanged during the review.

## Findings

### 1. P2 — identical erased blocks are rejected as reserved identities

**Location:** `IxIR0.Readdress.buildBlocks` (archive commit `7599a434`),
lines 279–295, and
`MutualBlock.runCertified` (archive commit `7599a434`),
lines 913–933.

`buildBlocks` puts all earlier generated block and member identities into
`protectedKeys`. `runCertified` then rejects any block digest already in that
set, without distinguishing an identical symbolic block from a different
preimage. Consequently distinct source constants that erase identically
cannot share their canonical IxIR₀ identity.

**Reproduction:** load the pinned upstream `addClosed` fixture, construct its
ordinary validated evaluation/erasure context, run `EraseAddressed.eraseGroups`,
and compare `MutualBlock.abstractMembers` for its mutual groups. Three distinct
source constants produce the exact same symbolic block:

```lean
[IxIR0.MutualBlock.Decl.defn .shared .erased]
```

The source addresses are:

```text
32f2ac930e7454a928442f5869ea8395086727cbdc3e9decd54103549a4dda64
dda919dce5be80e3fa24a2054b0a8e8fb61c8e66fc8826463846be1d88a6d172
f8aa65c951878450b60726a5967b39c0673bba0a9d821e1e254c1187177411de
```

All three produce block address
`577e8db9ffa18cd9b9f8fddb2686f1b775ca4ed418f0a20c2b83b946526577b0`.
The compiled probe compared the symbolic declarations for equality as well as
printing their hashes. This establishes repeated content as the trigger;
no BLAKE3 collision is needed.

**Impact:** the existing upstream `Nat.add` closure fails before erasure
certification. The original 17-constant Std slice reaches the same reported
boundary. The coverage gate passes because these are currently expected
rejections. Documentation accurately records the rejection, but its
"reserved-identity collision" description does not explain this ordinary
erasure-induced duplication.

**Recommended correction:** add checked reuse of exactly equal generated
blocks and their member identities. Preserve every producer-to-output mapping,
the block/image and environment-lookup audits, and protected oracle/stable
namespaces. Distinct preimages with the same digest must still reject.
IxIR₁'s whole-graph readdressing contract (`docs/ixir-content-addressing.md` at archive commit `7599a434`)
already distinguishes exact deduplication from conflicting content; use that
distinction without assuming its proof transports automatically to IxIR₀.

Acceptance should include a small repeated-erasure fixture, the unchanged
upstream bytes, complete address maps, and the existing namespace/collision
negatives. Advancing beyond this failure may expose a later coverage or
recursor boundary; it does not by itself establish `Nat.add` compilation.

### 2. P2 — a stale cache index undercharges the payload actually loaded

**Location:** `CacheDirIO.lookupRecord` (archive commit `7599a434`),
lines 179–210, and `CacheIO.readStore` (archive commit `7599a434`),
lines 127–157.

Lookup charges the indexed `expectedBytes` against `maxReadBytes`, then calls
the general `CacheIO.loadFileWith`. The loader uses the embedded store limits,
not the remaining directory-read allowance or indexed singleton length. Only
after loading the complete store does lookup check the record count and
payload size against the index.

**Reproduction:** write a canonical singleton store containing a one-byte
payload; index it with `maxReadBytes := 1`; replace it with a canonical
singleton store containing a 1 MiB payload; invoke the actual lookup with that
saved index. A temporary Lean elaborator referenced the existing private
lookup declaration to make the replacement deterministic, without modifying
the module or relying on a timing-sensitive concurrent test.

The compiled result was:

```text
indexedPayloadBytes=1 replacementPayloadBytes=1048576 maxReadBytes=1 charged=1
result=rejected: chunk payload size changed after directory indexing
```

A trace of the probe and its runtime threads confirmed reads of the complete
1,048,648-byte replacement file, including its 1,048,576-byte payload, before
that rejection. The original indexing read was a separate 71-byte file read.

**Impact:** changing a selected chunk between indexing and lookup can exceed
the promised per-run payload allowance. Replacing it with a multi-record
store also reaches the general loader before the singleton check. Individual
store limits and eventual semantic rejection remain in force, but the
documented selected-read bound (`docs/resource-budgets.md` at archive commit `7599a434`) does not cover this path.
The current directory tests exercise stable exact/one-below limits and
malformation before refresh, rather than replacement after indexing.

**Recommended correction:** enforce singleton framing, the admitted payload
bound, and the selected-read allowance while parsing the opened file, before
allocating its payload. A fresh metadata check alone leaves another race;
the streaming parser itself must enforce the bound. A bounded loader using
limits capped by the already-charged allowance is another possible approach.
Keep malformed selected chunks locally repairable within those limits.

Add deterministic changed-length and changed-record-count regressions at the
index/lookup seam, together with unchanged-file exact-boundary acceptance.

### 3. P2 planning — the next queue has no concrete source-coverage exit

**Location:** [M2c queue](roadmap.md#current-milestone-m2c), lines 36–52;
[C2 delivery](roadmap.md#c2-upstream-executable-acceptance), lines 354–380;
and [X1](roadmap.md#m3-executable-certification-and-self-hosting).

The queue describes the next source/native deliverables, but its remaining
rows are E1/E2, F1, I2, and deferred A1. C2 has delivered three unchanged
upstream closures through baseline IxIR₂. Their native selection still fails
at `missingConstructorSchema`; upstream addition and explicit recursion have
earlier, distinct failures. N2 provides a strong runtime-input result for a
synthetic reversal schema. No current package names the next upstream program
to advance through these boundaries.

This leaves the practical path to X1's "suitable accepted native family"
unscheduled. Encoding and resource proofs can improve the existing endpoint
without increasing the compiler's upstream source reach.

**Recommendation:** add a C3 successor with a pinned input, current failing
stage, and an observable next accepted stage. Start with the exact-block issue
above, then choose one unchanged upstream computational entry to carry through
checked source, physical execution, and native selection. Record newly exposed
boundaries separately, retain negative neighbors, and require complete fresh
artifacts, result agreement, and reclamation at each claimed exit.

Keep this source track alongside E1/E2. A small measurement gate should name
the accepted inputs that will supply compile/check cost, artifact growth,
runtime counters, and native measurements before activating M2d. Broad
recursion recovery, shared native borrowing, and representation work should
follow the needs of that selected input.

### 4. P3 documentation — the roadmap again duplicates delivery narratives

**Location:** [delivered baseline](roadmap.md#delivered-baseline-and-continuing-limits),
especially lines 260–401, and the corresponding focused source/credit documents.

The compact baseline table is followed by roughly 140 lines of detailed B1,
B2, N2, C2, and R6 delivery records. Those repeat theorem scope, fixture counts,
negative cases, and dated build totals already maintained in the focused
specifications and validation guide. This conflicts with the roadmap's own
compact-delivery/successor rule and increases the number of places each
extension must update.

**Recommendation:** retain a compact scoped row and links for each delivered
package. Keep detailed contracts and dated validation evidence in their
focused documents, and put each concrete successor in the active queue.
The separation between roadmap, compiler design, and development procedure
otherwise works well; recreating a separate planning hierarchy would add
another authority to maintain.

## Recommended sequencing

1. Correct cache read accounting and add the replacement regressions. This is
   a small resource-policy repair independent of compiler-language growth.
2. Land checked exact-block reuse as the first C3 acceptance step, preserving
   unchanged upstream fixtures and all namespace/provenance obligations.
3. Begin E1 with the load/store/branch forms used by the actual N2 output and
   extend through stream/PC/relocation and object obligations. Record the S0
   readiness decision before substantial ISA growth.
4. Name C3's first upstream native computation and measure its compilation and
   execution. Use observed failure stages and costs to select subsequent
   recursion, ownership, and representation extensions.
5. Activate F1 when broadening allocation or calls, with occupied reservations
   and stack demand in the bound. Activate I2 before independent IxIR₂
   persistence or artifact-root comparison; retain A1's real-CFG trigger.

Keep the existing conditional gates for effects, linking, executable checking,
theory integration, self-hosting, and zk. The current evidence does not justify
moving broad specialization, mixed field worlds, threads, or additional ISAs
ahead of the concrete source/native path. Compress delivered roadmap prose
when recording these successors.
