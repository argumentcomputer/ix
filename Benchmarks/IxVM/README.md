# Focused ixVM execution regressions

`bench-ixvm-focus` isolates a completed `ix-refine/0` report's failed singleton
**blocks**, including all projections of a mutual block. It prepares a full
refined manifest; it does not execute anything or claim that skipped constants
have passed. A useful regression loop is to prepare once, then reuse this
manifest and selection across frozen executor binaries.

```sh
lake build bench-ixvm-focus
lake exe bench-ixvm-focus --self-test
lake exe bench-ixvm-focus ENV.ixe ORIGINAL.ixes OLD-FAILURES.json FOCUSED.ixes
# Use the selection printed by the preceding command:
IX_AIUR_EXEC_MAX_BYTES=137438953472 \
  lake exe ix check --ixe ENV.ixe --ixes FOCUSED.ixes \
  --shards SELECTED_IDS --jobs 1 --keep-going --report focused-report.json
```

Use fresh output paths. The helper checks the source-manifest digest, environment
path/size, singleton membership and uniqueness. Existing Rust refinement
recomputes the partition metadata and aggregation tree, and checks complete,
disjoint block coverage. The execution command still runs native whole-env
content-address/ownership validation before checking only the selected leaves.
Dependencies remain available as the normal shard frontier. Unselected leaves
are reported `unchanged`, not checked or proven. This is a diagnostic test, not
a substitute for a subsequent full-partition execution or proof run.

Native coverage/ownership setup uses its own temporary pool (up to 8 available
CPUs by default), even with `--jobs 1` or `RAYON_NUM_THREADS=1`. Set
`IX_AIUR_SETUP_THREADS` to a positive count to override setup parallelism.
The setup pool is dropped before creating the execution pool; `--jobs` still
controls the number of execution workers. This changes neither validation nor
which leaves execute.

`FOCUSED.ixes.focus.json` records exact target block addresses, original labels
and failure reasons, source/refined manifest hashes, and the reusable selection.
The report must contain completed singleton failures: a still-running parent or
an incomplete split report is not a valid input. Memory-budget failures are
resource limits, not kernel rejections. An already passing report has no targets;
reuse the earlier failure report to retain historically expensive regressions.

For the Anthropic FLT campaign, the historical report is
`ixvm-shard504-carry-add.y9PfMu/report.json`: 270/274 constants passed and four
singleton blocks hit 32 GiB. The subsequent byte-packed 128 GiB baseline
`ixvm-shard504-compact128.K21HOd` passed all 274 via three final parts in
48m 36.5s. Those four blocks remain the focused optimization regression set;
they are no longer unresolved execution failures.

Keep an OS/cgroup memory cap and wall-clock deadline in addition to the record
limit. The record limit measures accounted execution storage, not total RSS or
the much larger analytic peak of a future STARK proof. No proof is generated by
these execution tests.

## Completion-driven execution refinement

Native full/selected partition checks use one completion queue, execution pool,
admission controller and shared record budget for the entire check. A parent
that hits its own record limit releases its record and permit before its two
children are queued; it no longer waits for every other original shard to
finish. Splitting still occurs only between whole blocks, including their
mutual projections. Children join the FIFO ready queue; fit-aware backfilling
and larger tail-tier grants are separate, unimplemented policies.

A shared-budget failure is different: admission pauses until current attempts
drain, then retries that unchanged claim, with the existing maximum of two
pressure retries. It does not split merely because peers consumed the shared
budget. A still-oversized singleton and an ordinary kernel rejection remain
failures. No running record is suspended, resumed, or given a larger limit.

Admission and completion waits stay outside Rayon, leaving workers available
for nested witness work. Active tasks plus unconsumed completion messages are
bounded by pool width. The dispatcher drains all launched work on an error;
it never returns partial success. Under unwind builds, worker panics become
dispatcher errors after cleanup; panic-abort and OOM still terminate the process.
Live headroom, growth forecasts, recovery delays and record limits remain in
force, including the serial fallback when telemetry is unavailable.

Admission diagnostics report the backoff reason, full memory-PSI sample and
ten-second trend, swap growth and remaining recovery delay. A brief >10% PSI
sample pauses admission immediately and reduces concurrency, but does not
restart the five-second cooldown by itself: recurring short system-wide spikes
must not starve otherwise well-provisioned serial work. Sustained >10% PSI
(`full avg10`), process swap growth and insufficient live headroom still require
recovery. Every new shard must still fit the live reserve, outstanding
reservations and growth forecast. A 30-second idle timeout reports the actual
reason and next reservation; it does not silently bypass the gate or declare
partial coverage successful. See [Linux PSI](https://docs.kernel.org/accounting/psi.html)
for the distinction between short stall samples and the average trend.

Progress identifies each shard label, pressure-attempt number and generation.
The `N/M shards settled` counter refers to original selected shards: a split
parent settles only after all descendants finish. Settled can include failures;
use the final report, not the progress fraction, to determine success.

Native audit reports include `scheduler: "completion-driven"`, `executed`
(all attempts), and `max_generation` (maximum split/retry lineage length).
`waves` is `null` because this path has no batch-wave barriers. Final child
labels and ownership are sorted deterministically, regardless of completion
order. Unselected leaves remain `unchanged`; an aborted parent's predicted
proof peak is not fabricated from its children's peaks. Paths that still need
the legacy Lean driver, such as destination-prover-budget refinement, retain
that driver and its numeric wave count.

## Compact multiplicity prototype

Set `IX_AIUR_COMPACT_MULTIPLICITIES=1` to retain function and memory-query
counters in `u32` segments. The default remains full-field storage while we
compare throughput and memory on focused FLT and ordinary workloads. The flag
is read once per process; use separate invocations for on/off comparisons.

Counters still have field semantics: a larger initial value or a hit past
`u32::MAX` widens only that segment to full fields, without truncation,
saturation, or changes to query order, memory pointers, hint promotion, or
witnesses. New segments may start narrow again. A widened segment stays wide
after field wrap. Widening reserves both old and replacement storage before
copying; refusal is a typed resource limit, even on a memo hit, and leaves
that map's rows and encoding unchanged. It is not a successful check or a
resumable partial record. This does not change scheduling or shard limits.

Use the same input, manifest, selection, limits, and worker counts for each
comparison; leave profiling disabled for clean execution timings:

```sh
IX_AIUR_COMPACT_MULTIPLICITIES=1 IX_AIUR_EXEC_MAX_BYTES=137438953472 \
  lake exe ix check --ixe ENV.ixe --ixes FOCUSED.ixes \
  --shards SELECTED_IDS --jobs 1 --keep-going --report compact-report.json
```

## Ordinary and Mathlib controls

Reuse a current-format Mathlib environment to extract small dependency closures
with the native CLI; this does not rebuild Mathlib or modify the source `.ixe`:

```sh
lake exe ix shard extract MATHLIB.ixe \
  --consts Nat.add_comm,List.map_map --out CORE.ixe
lake exe ix shard extract MATHLIB.ixe \
  --consts Nat.exists_infinite_primes --out PRIME.ixe
lake exe ix shard CORE.ixe --shards 1 --out CORE.ixes
lake exe ix shard PRIME.ixe --shards 1 --out PRIME.ixes
```

Use fresh output paths. Extraction preserves dependency closure and whole mutual
blocks. An incompatible older `.ixe` needs recompilation or replacement with a
compatible artifact; changing its header is not a format conversion. Extraction
from the full environment can itself require substantial RAM, so finish it before
starting timed execution comparisons.

Then compare separate invocations with compact counters disabled/enabled, using
the same frozen binary, fixtures, manifests, limits and worker counts:

```sh
IX_AIUR_COMPACT_MULTIPLICITIES=1 IX_AIUR_MULTIPLICITY_STATS=0 \
  IX_AIUR_SETUP_THREADS=2 IX_AIUR_EXEC_MAX_BYTES=8589934592 \
  RAYON_NUM_THREADS=1 LEAN_NUM_THREADS=1 \
  ./FROZEN-IX check --ixe PRIME.ixe --ixes PRIME.ixes --jobs 1 \
    --report PRIME-compact-report.json --json PRIME-compact-results.json
```

Unset `IX_AIUR_QUERY_STATS` for clean timings too. Repeat in alternating order,
including the pre-change binary when available. Check exit status, zero failures,
complete ownership, claim equality, and unchanged predicted proof cost; do not
infer these from timing output alone. Keep final profiling scans separate from
timing controls, and distinguish encoded counter payload from peak RSS. Tiny
fixtures can be dominated by startup and allocation noise. These controls execute
only the extracted closures, not full Mathlib or a STARK proof.

## Multiplicity-storage diagnostics

Use `IX_AIUR_MULTIPLICITY_STATS=1` on a focused run to scan multiplicity
storage at execution return or rejection. Both generated Rust and bytecode
execution support it (also the generated recursive verifier and aggregator).
Leave it unset for timings used to compare executor optimizations.

```sh
IX_AIUR_MULTIPLICITY_STATS=1 IX_AIUR_EXEC_MAX_BYTES=137438953472 \
  lake exe ix check --ixe ENV.ixe --ixes FOCUSED.ixes \
  --shards SELECTED_IDS --jobs 1 --keep-going --report profile-report.json
```

The `[aiur-multiplicity]` stderr records contain totals for all function and
memory maps, plus at most the 32 largest maps by counter-row count. Temporary
storage is proportional to the number of maps, not the number of query rows;
the linear scan reads only initialized counters and never runs on progress
ticks. `scan_us` reports its cost. Separate these profiled timings from clean
runs; scanning a large record still takes time and reads memory.

- `counts`: disjoint canonical multiplicity bins, in order: 0, 1, 2–255,
  256–65535, 65536–u32::MAX, and larger.
- `segment_maxima` / `segment_rows`: segments / initialized rows whose
  current maximum needs 1, 2, 4, or 8 bytes, in that order. This exposes the
  widening impact of a rare large count in an otherwise small-count segment.
- `full_payload_bytes`: equivalent eight-byte counter payload, excluding page
  rounding, spare capacity, and other table storage.
- `adaptive_payload_lower_bound` / `u32_payload_lower_bound`: hypothetical
  segment-wide encodings of the snapshot, not measured allocations or RSS
  savings. They omit allocation overhead and historical widening before a
  field wrap. These remain estimates even with compact storage enabled.
- `stored_payload_bytes` / `stored_segments_u32_field`: actual initialized
  encoded payload / segment counts in u32 and full-field form. Unlike the
  snapshot lower bounds, these include segments kept wide after field wrap.
  Payload excludes unused capacity, page rounding, and allocation metadata;
  it is not the record's accounted allocation or process RSS.
- `canonical_sum`: sum of current canonical field values, not a lifetime
  call/update count. Initialization, unconstrained hints, and field wrap matter.
- For budgeted execution, `accounted_bytes`, `reservation_peak_bytes`, and
  `record_limit_bytes` describe the whole record's accounting, not its RSS or
  predicted prover peak. The reservation peak includes transient charges and
  local reservations rolled back when the shared budget refused them.

`status=returned` means execution returned, not that a STARK proof was made.
`resource-limit` / `rejected` profiles describe partial, unsuccessful records.
Failure before a record is constructed cannot supply a counter snapshot.
The diagnostic is read-only: it does not alter grants, filtering, refinement,
query semantics, or which claims must pass. It is intended to guide compact
counter experiments, not to serve as an admission bound.
